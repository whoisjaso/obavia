# Obavia auction Worker

Payments run on Whop (`src/whop.ts`): the deposit is a Whop payment held and refunded on a loss; the balance is a Whop invoice; the dealer is paid by a transfer to a connected account; Whop's signed webhooks are the only way money news enters.

Cloudflare Worker + one Durable Object per lot. The object runs the same rules as the app (`../src/engine/auction.ts`) with the authority: a bid is one transaction that writes the price, the close time and the ack together; the ack is what the phone thumps on. The close is an alarm plus a read-time check. Every connected phone gets the lot on every change over a hibernating WebSocket. D1 holds a copy of every lot and every bid, never read on the bid path.

Every dealer route above (and the object's `/copy`) answers 403 `not_your_lot` to a dealer key that is not the lot's dealer, whatever the lot's state, closed and sold included. The admin key passes.

## The sale and the dealer's $250 (migration 0011)
The deposit on a sale (`lot.sale.deposit`): `held` from the hammer; `applied` at the engine start (the $250 counts toward the price, so the balance the phone shows, the total less $250, is the whole of what the buyer brings, and the $250 is the dealer's); `to_dealer` on a forfeit; `released` on a void. The buyer's record (`buyers.deposit_status`) follows: `applied` at the start (so `POST /me/deposit/release` is refused, 409 `nothing held`), `forfeited` on a forfeit.

`lot.sale.payout = { state: 'owed' | 'sent' | 'paid', transferId?, method?, at? }` on an applied or forfeited sale, one row in `dealer_payouts` (lot, dealer, buyer, amount 250, reason `applied`, `forfeit` or `no_pay`, `held`, state, transfer id). When the dealer has a connected account (`dealers.whop_account`) and Whop is configured, the object transfers $250 on Whop with the idempotency key `applied:<lot>` or `forfeit:<lot>` and records the transfer id (`sent`, money event `payout.sent`); otherwise, or when Whop refuses (the error is kept on the row), it stays `owed`. `held` is 0 when the buyer's deposit was not captured at that moment (refunded, disputed, or already taken by another sale); nothing is sent for such a row.

`dealer_payouts` is the record; the lot follows it. When the row moves outside the object (paid by hand, or sent by the retry), the Worker posts `{ id, state: 'sent' | 'paid', transferId?, method?, at }` to the lot's object at `POST /payout` after its D1 write. The object takes it only from the Worker (no `x-dealer`; a dealer key is 403, and the Worker never forwards `/lots/:id/payout` from outside: 404), only for the lot's own payout id (409 `wrong_payout`, `no_payout`), and only once: the same news again answers the same lot, other news on a settled payout is 409 `payout_settled`. A failure there leaves the row as written and the Sold page one step behind. `src/engine/meta.ts`'s `Payout` type still says `'owed' | 'sent'`; the object's `LotPayout` is the wider shape the wire carries.

The pay window is 48 hours from the hammer (`PAY_WINDOW_MS`; the standing value under decisions §7 and the growth plan's 2026-10-12 changelog row until the owner rules). The object's alarm pushes the winner at 24 h and at 6 h before the deadline, to screen `won`: "Pay by Sat 8 pm · $5,331 · 24 h left" (the day and hour in Central time with the minutes dropped, as the Won screen says it; the balance is the out-the-door total less $250). The "Yours" push at the hammer carries the same "Pay by" words. At the deadline with no payment the sale forfeits through the forfeit path with reason `no_pay`. A forfeit pushes the buyer "Deposit forfeited · 2014 Nissan Altima" (screen `me`) and the dealer's Desk, when it has a token on `dealers.push_token` (`POST /dealers/push`), "Deposit forfeited · <car> · $250 is yours".

Money events written by the object: `balance.paid_at_lot` (`paid:<lot>`), `deposit.applied` (`applied:<lot>`), `deposit.forfeited` (`forfeit:<lot>`, with `reason`), `deposit.released` (`release:<lot>`), `payout.sent` (`payout:<key>`). Each is written before the sale's state moves; a failed write fails the request (or retries the alarm).

The check stops the honest mistake and the lazy shill; the deposit's payment instrument is the next match to add. Keys are idempotency keys: a retried request returns the same ack. The buyer's ceiling never leaves the object.

## Buyer tokens (migration 0009)
A token is `<id>.<sig>` at epoch 0 and `<id>.<epoch>.<sig>` after, HMAC-SHA-256 with `BUYER_SECRET` over everything before the last dot. `buyers.token_epoch` is the epoch in force; a token signed for another epoch is refused (401 `sign in`) on every buyer route. The bid path reads the epoch in the admission read it already makes; every other buyer route makes one D1 read. Tokens minted before 0009 are epoch 0 and keep working.

Refused re-mints are logged in `token_refusals`, not `bid_refusals`: there is no lot, and `presented` (`none`, `forged`, `other`, `stale`) and `known` (the id exists) are what the admin needs to tell a lost phone from a takeover attempt.

`DEV=1` keeps the old path for `wrangler dev`, the tests and the app's local fixtures: `POST /me` with any `id` and no credential mints that id's token at its current epoch. Never set `DEV=1` on a deployed Worker: a stranger could take any buyer.

What the app must send (the phone task):
1. First launch, nothing stored: `POST /me`, `content-type: application/json`, no `authorization`, body `{ "name": "...", "state": "TX" }`. Store `id` and `token` from `{ id, token }` in secure storage. Do not send a device id.
2. Every later launch: `POST /me`, `authorization: Bearer <token>`, body `{ "id": "<stored id>", "name": "...", "state": "TX" }` (or `{}` with the token alone). 200 is `{ id, token }`; keep the token it returns.
3. A 401 `not_yours` on step 2 means the stored token is dead (rotated or bumped). Until Phase 2 there is no way back to that id; the app says so and does not start a new buyer on its own.
4. Rotation: `POST /me/rotate`, `authorization: Bearer <token>`, no body → `{ id, token }`; replace the stored token before using it again.
5. The first bid ever: `POST /me/phone` `{ "phone": "+12145550142" }`, then `POST /me/phone/verify` `{ "code": "123456" }`, before the licence and the deposit. A 409 `phone_required` on a bid reopens the phone page. Keep only what `GET /me` returns (`phone`, the last four, and `phoneVerified`).

## The nightly reconciliation
Cron `0 8 * * *` (03:00 Central in daylight time, 02:00 in standard time) runs `src/reconcile.ts`: every lot's D1 copy against its object on high, bids, closesAt, leader, closed and sale; a differing copy is rewritten by the object itself, its id recorded in `differing` and each field that differed, with both sides, in `differences` (migration 0014). Deposits held (`captured`) against the Whop USD ledger balance (`GET /ledger_accounts/{WHOP_ACCOUNT_ID}`, settled balance only; pending and reserve are noted, not counted). Payouts owed (`dealer_payouts` with `state = 'owed'` and `held = 1`) are liabilities beside the deposits: `equal` is 1 when no copy differed and the balance is unknown or at least $250 × deposits held plus the payouts owed. One row per run in `reconciliations` (the nightly row), with `payouts_owed`, `payouts_owed_cents` and `differences`. Before it, the cron sends every payout left owed to a dealer with a connected account. `GET /admin/reconcile` reads the rows and the streak (`equalNights`, `sevenEqual`); `GET /admin/exposure` keeps the last seven rows as before.
